# 代码评审

`/code-review` 让另一个 agent 读工作区里未提交的改动，你继续用这段对话。它复用这个工作区里已经在跑的评审者，
所以后一轮知道前一轮发现了什么。

```text
/code-review
/code-review src/api.py 里的错误处理
```

命令后面写的是关注点。什么都不写时，它找的是任何会让这次改动出错或难以保留的地方。对话里显示的是你打的命令，
不是模型写的那段提示。

## 会发生什么

1. 模型用 `git status --short` 和 `git diff HEAD` 收集改动，并读属于这次改动的未跟踪文件。
2. 它找这个工作区的评审者，没有就用 `zettcode daemon spawn --name code-review` 起一个。
3. 它用 `send_message` 把请求发给评审者。评审者按 `file:line` 报意见：正确性、错误处理、测试、命名，改什么、
   为什么。
4. 你来改。模型把新的状态发给同一个评审者，如此往复，直到它没有可说的。
5. 每条请求都要求评审者回答。某一轮没有回答，就再发一次；还没有，模型就从它的存档对话里读最后一条消息，
   汇报出来，并停掉评审者。

评审者被要求只读不改：不编辑、不写文件、不提交。这是一句指示，不是沙箱。

## 评审者拿到哪一档 shell

评审者用你的 shell 档位跑；你的是 `ask` 时用 `safe`，因为后台进程没有人可以问。

| 你的档位 | 评审者 |
| --- | --- |
| `full` | `full` |
| `safe` | `safe` |
| `ask` | `safe` |
| `deny` | 不启动；模型自己读文件，并说明读了哪些 |

## 什么时候不适合

- 工作区不是 Git 仓库，或者没有未提交的改动：没有东西可收集。
- 你想评审的是一个分支或一次提交，而不是工作树。
- 你不想让第二个会话花 token。一次评审用一个 daemon，直到你停掉它。

评审者是一个普通的已保存会话，没停掉之前都列在 `zettcode daemon list` 里。见[后台 agent](/zh/guide/daemons)。
