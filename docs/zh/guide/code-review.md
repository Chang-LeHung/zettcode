# 代码评审

`/code-review` 让模型评审工作区里未提交的改动，并用另一个会话做评审者。这条命令只写一段提示，当成你这段对话里的一轮跑起来，
就像你亲手打的一样。之后的一切都是模型在这段提示的指引下完成的。

```text
/code-review
/code-review src/api.py 里的错误处理
```

命令后面写的就是关注点。什么都不写时，关注点是"任何会让这次改动出错或难以维护的地方"。对话记录里显示的是你输入的命令，不是那段提示。

## 一步一步发生了什么

1. **收集改动。** 提示让模型运行 `git status --short` 看改了什么，运行 `git diff HEAD` 取补丁，并读取属于这次改动的未跟踪文件。
2. **找到或启动评审者。** 模型先看 `<daemon> list`，找这个工作区里已有的评审者。命令给它起的名字是 `code-review`，有就复用：
   读过前几轮的评审者已经熟悉这次改动。只有没有时才运行 `<daemon> spawn --name code-review`。`list` 里看到的是名字和工作区，
   所以同一工作区里另一个终端起的评审者也会被复用。
3. **发出请求。** 模型用 `send_message` 告诉评审者读什么，答复作为一条消息回来时再汇报。提示要求意见用 `file:line` 点名具体问题：
   正确性、错误处理、测试、命名，说明打算怎么改、为什么，不要复述 diff。
4. **修完再来一轮。** 修改期间评审者一直保持运行。主 agent 把意见改完后，把改动的新状态发给它，如此往复，直到评审者没有可说的为止。
5. **每条消息都写明评审者必须回答。** 它要么把意见发回来，要么用一个词说明没什么要改的。一个不出声的评审者，和一次什么都没发现的评审无法区分。
6. **某一轮没有回答时。** 请求会再发一次。如果仍然没有回答，模型就去读评审者自己的会话 `~/.zettcode/sessions/*/<session id>/data.jsonl`，
   其中最后一条 assistant 消息就是它的评审。模型把它汇报出来，然后用 `<daemon> kill <session id>` 停掉评审者，免得一直跑着。
   `<daemon> list` 能看到有什么在运行。
7. **如果启动不了 daemon，** 模型会说明原因，然后自己做评审。

`<daemon>` 是终端自己所运行的那套安装的命令，即同一个解释器下的 `python -m zettcode.daemon`，而不是在 `PATH` 里找到的 `zettcode`。
所以只有当前终端能看到的代码检出或虚拟环境，也能启动评审者。

## 评审者拿到什么 shell 级别

评审者运行在**你自己的 shell 级别**上，绝不会更高。

| 你的级别 | 评审者 |
| --- | --- |
| `full` | 以 `full` 启动 |
| `safe` | 以 `safe` 启动 |
| `ask` | 以 `safe` 启动：`ask` 的意思是"问读者"，后台进程没法问 |
| `deny` | 不启动：没有 shell 就没法收集 diff，所以模型直接读文件评审，并说明读了哪些 |

提示会告诉评审者它只读不改：不编辑、不写文件、不提交、不运行会修改工作区的命令。改动由主 agent 在拿到意见后自己做。
这只是一句指示，不是沙箱：`full` 下的评审者如果真去改，是有权限的。

## 什么时候不适合

- 工作区不是 Git 仓库，或者没有未提交的改动：提示用 `git status` 和 `git diff HEAD` 收集改动，没有东西可读。
- 你想评审一个分支相对另一个分支的差异，或者已经提交的某次提交。这条命令评审的是未提交的改动；可以在关注点里写明你要的，或者用平常的话直接说。
- 你不想启动后台会话。每次评审都用到一个 daemon，评审者的每一轮也会花模型 token。

每个 daemon 都是一个普通的已保存会话，所以没停掉的评审者会一直列在 `zettcode daemon list` 里，直到你停止它。
启动、停止和查看 daemon 见[后台 agent](/zh/guide/daemons)。
